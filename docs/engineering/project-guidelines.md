# Project Guidelines

Документ фиксирует устойчивые архитектурные и код-стайл правила проекта. Детали скриптов, CI и deploy описаны отдельно в [Scripts Directory Guide](../tech/scripts.md).

## Project Structure

```text
Compound Interest/
├── App/
├── Core/
├── Flows/
├── Infrastructure/
├── Model/
│   ├── Database/
│   ├── Domain/
│   └── DTO/
├── Common/
│   ├── Extensions/
│   ├── Helpers/
│   └── View/
└── Resources/
```

Обязательные правила:

- `App` содержит только lifecycle-типы и точку входа приложения.
- `Core` содержит переносимые сервисы без зависимости от предметной области проекта.
- `Flows` содержит экраны, entry views, view models, presentation-модели, presentation-extensions доменных типов и остальной feature-specific UI.
- `Flows/App` содержит корневую композицию приложения и app-scoped UI, который не относится к отдельному бизнес-flow.
- В корне папки экранного flow обычно храним entry `View` и, если экран владеет состоянием, соответствующую `ViewModel`.
- Feature-specific UI, который не является отдельным экраном, может жить в собственном flow-каталоге без обязательного `ViewModel`, как набор переиспользуемых presentation-компонентов.
- Дочерние views конкретного flow размещаем в его подпапке `Views`, а presentation-модели — в подпапке `Models`.
- Подпапки `Views` и `Models` создаём только при наличии соответствующих типов; пустые структурные директории не добавляем.
- `Infrastructure` содержит проектно-специфичные реализации доступа к данным, persistence и network infrastructure.
- `Model/Database` содержит persistence-модели, `Model/Domain` — доменные типы, `Model/DTO` — сетевые транспортные модели.
- `Common` содержит только универсальные extensions, helpers и views, которые уже переиспользуются внутри проекта.
- Extensions проектных доменных моделей не относятся к `Common`; presentation-свойства таких моделей размещаются внутри `Flows`.
- `Resources` содержит assets, локализации, plist и сгенерированные ресурсы. Код в `Resources/Generated` не редактируем вручную.
- Структура тестового target зеркалирует соответствующие production-слои.
- Не создаём `.gitkeep` для пустых структурных директорий: директория появляется в Git вместе с первым содержимым.

## Assets

Проект использует встроенную Xcode/Swift кодогенерацию для доступа к ресурсам из asset catalogs.

Обязательные правила:

- К картинкам и цветам обращаемся через сгенерированные Swift symbols.
- Не используем строковые имена ассетов вроде `Color("Button/primary")` или `Image("iconName")`.
- Исключение — `SFSymbols`: системные символы Apple допускается создавать строками, например `Image(systemName: "chevron.right")`.
- Если Swift symbol для ассета не генерируется, нужно исправить структуру asset catalog или настройки проекта, а не обходить проблему строкой.

Пример предпочтительного доступа к цветам:

```swift
Color(.Button.primary)
Color(.Button.secondary)
```

Пример нежелательного доступа к цветам:

```swift
Color("Button/primary")
Color("Button/secondary")
```

## Swift File Structure

Внутри Swift-файлов используем `// MARK: -` для навигации и явного разделения ответственности. Этот раздел — единственный источник правды по списку секций, их порядку и правилам применения.

По умолчанию один Swift-файл содержит один основной top-level тип.

Обязательные правила:

- Самостоятельные `View`, модели, сервисы и другие типы размещаем в отдельных файлах.
- Не объединяем несколько самостоятельных типов в одном файле только потому, что они используются рядом.
- Имя файла должно совпадать с именем его основного типа.
- В том же файле допустимы extensions основного типа и его небольшие приватные вспомогательные типы, если они не имеют самостоятельного назначения.
- Если вспомогательный тип начинает переиспользоваться, разрастается или получает отдельную ответственность, выносим его в собственный файл.

Секции не должны добавляться механически. Если раздел пустой или в типе всего несколько строк, `MARK` не нужен.

Рекомендуемый базовый набор секций:

```swift
// MARK: - Typealias
// MARK: - Outputs
// MARK: - Inputs
// MARK: - Properties
// MARK: - Computed properties
// MARK: - Observable properties
// MARK: - Init/Deinit
// MARK: - Layout
// MARK: - Private methods
// MARK: - Public methods
// MARK: - Constants
// MARK: - Preview
```

Реализацию каждого протокола всегда выносим в отдельный extension и маркируем именем протокола. Объявление conformance и реализация всех требований протокола должны находиться в этом extension, а не в основном теле типа:

```swift
// MARK: - Identifiable

extension Model: Identifiable {}
```

## MARK Policy

`MARK` — инструмент навигации, а не ритуал. Хороший `MARK` помогает быстро понять структуру типа; плохой создаёт шум.

Форматирование секций:

- После `// MARK: - ...` всегда ставим одну пустую строку.
- Между секциями оставляем одну пустую строку.
- Если внутри типа используются `MARK`, после открывающей `{` типа оставляем одну пустую строку.
- Перед закрывающей `}` типа пустую строку не ставим.
- Внутри одной секции пустые строки используем только для смысловых групп.

Используем секции, когда они реально отделяют разные виды ответственности:

- `Typealias` — локальные алиасы типа, особенно для callback/output closure типов.
- `Outputs` — события наружу: closures, delegates, publishers, callbacks.
- `Inputs` — зависимости и входные данные, которые приходят извне и управляют типом.
- `Properties` — stored/static properties без UI-observation semantics.
- `Computed properties` — вычисляемые свойства без хранения состояния.
- `Observable properties` — `@State`, `@Binding`, `@Published`, `@ObservedObject`, `@StateObject`, `@Environment` и похожие observable wrappers.
- `Init/Deinit` — инициализация, deinitialization и setup, который логически является частью жизненного цикла.
- `Layout` — `body`, `ViewBuilder`-части и layout-only helpers во `View`.
- `Private methods` — приватная логика типа.
- `Public methods` — внешний API типа, включая значимые `internal` методы.
- `Constants` — нижний блок файла с приватными extensions для файловых констант.
- `Preview` — блок SwiftUI preview в конце файла.
- `ProtocolName` — отдельный extension с conformance конкретному протоколу.

Не используем секции, если они ухудшают читаемость:

- не добавляем пустые секции;
- не дробим маленький `View` на 5 разделов ради формальности;
- не прячем один `body` под `Layout`, если файл очевиден без этого;
- не смешиваем protocol conformance с внутренними секциями основного типа.

## Initialization

Не добавляем отдельные initializer или default-значения параметров только ради preview или тестов. Preview и тесты используют production initializer и явно передают необходимые объекты, mock-реализации или test doubles.

## SwiftUI Preview

Каждый production `View` должен иметь preview в том же файле. Preview — часть контракта представления: он документирует поддерживаемые состояния и позволяет проверить их независимо от родительского экрана.

Обязательные правила:

- Для каждого конкретного `View`, включая экран и самостоятельный дочерний компонент, добавляем `#Preview` в конце его файла.
- Перед preview ставим `// MARK: - Preview`. После preview в файле не размещаем production-код.
- Preview должен покрывать все поддерживаемые визуально или поведенчески различимые состояния `View`: например, empty, loading, content, error, selected, disabled, focused, минимальные и граничные данные, если они меняют отображение.
- Если комбинаций состояний много, выбираем минимальный набор сценариев, который покрывает каждое различимое состояние и значимую layout-границу. Не создаём декартово произведение комбинаций, которые выглядят и ведут себя одинаково.
- Каждое состояние показываем с реалистичными данными. Пустая заглушка допустима только как отдельный empty-state сценарий, который действительно поддерживает `View`.
- Несколько состояний размещаем рядом в одном `#Preview` либо оформляем отдельными именованными `#Preview`, если так их проще читать и проверять.
- Статические bindings передаём через `.constant(...)`. Интерактивное preview-состояние объявляем непосредственно внутри `#Preview` через `@Previewable @State`, `@Previewable @FocusState` и другие подходящие property wrappers.
- Не создаём отдельный `View`-контейнер только для хранения preview-состояния. Если локального preview-кода технически недостаточно и нужен отдельный helper или test double, он должен быть lightweight, находиться в том же файле и быть изолирован от release-сборки через `#if DEBUG`.
- Не протаскиваем реальные production dependencies, сеть, постоянное хранилище или тяжёлую runtime-инфраструктуру в preview. Используем constants, mock data, in-memory реализации и lightweight test doubles.
- Отсутствие preview допустимо только при подтверждённой технической невозможности создать `View` изолированно. Причину явно фиксируем при ревью; сложная инициализация сама по себе является поводом упростить зависимости `View`, а не молча пропустить preview.

Предпочтительный формат интерактивного preview с несколькими состояниями:

```swift
// MARK: - Preview

#Preview {
    @Previewable @State var value = "100 000"

    VStack {
        AmountInputView(value: $value, isDisabled: false)
        AmountInputView(value: .constant(""), isDisabled: false)
        AmountInputView(value: .constant("100 000"), isDisabled: true)
    }
}
```

Если состояния удобнее проверять изолированно, используем именованные варианты:

```swift
#Preview("Content") {
    ResultView(state: .content(.preview))
}

#Preview("Empty") {
    ResultView(state: .empty)
}

#Preview("Error") {
    ResultView(state: .error("Не удалось загрузить данные"))
}
```

## View Responsibility

Каждый flow строим по MVVM. View layer максимально декомпозируем на небольшие компоненты с одной ответственностью, чтобы экран собирался из них как из LEGO-блоков.

Обязательные правила:

- У каждого flow есть `ViewModel`, которая владеет состоянием экрана, обрабатывает пользовательские события и управляет сценарием flow.
- Бизнес-логика flow не размещается во `View`: её выносим во `ViewModel` или в отдельный доменный сервис, который вызывается из `ViewModel`, если логика переиспользуется или имеет самостоятельную ответственность.
- Большой `View` декомпозируем на самостоятельные views по визуальным блокам и пользовательским сценариям.
- Декомпозиция должна снижать сложность и улучшать повторное использование; не создаём отдельный тип ради нескольких строк без самостоятельной ответственности.
- Не каждый flow обязан иметь собственный `ViewModel`: для изолированных presentation-блоков без самостоятельного сценария достаточно `View` и локальных helpers.

SwiftUI `View` отвечает только за отображение состояния и передачу пользовательских событий. Presentation views должны оставаться максимально dumb.

Обязательные правила:

- Presentation view принимает данные, отображает их и сообщает о действиях пользователя, но не владеет бизнес-логикой, orchestration и lifecycle-решениями родителя.
- Пользовательские события передаём во `ViewModel` через методы-намерения или из дочернего компонента наружу через closures.
- View не должен менять состояние родителя через `Binding`, если он не является control-компонентом.
- `Binding` используем для компонентов, которые редактируют значение как часть своего назначения: `TextField`, `Toggle`, `Slider`, picker, custom input controls.
- Для одноразовых событий используем closures: `action`, `onTap`, `onRetry`, `onClose`.
- Показ, скрытие, таймеры, async lifecycle и orchestration должны жить у владельца состояния: parent view, view model или coordinator.
- Локальное UI-only состояние допустимо внутри `View`, если оно не является бизнес-состоянием и не нужно снаружи.
- Если presentation view начинает принимать много bindings/actions или содержит async-сценарии, это сигнал пересмотреть границу ответственности.

## Layout Metrics

Отступы задаём только через объект `Margin`.

Обязательные правила:

- Не используем literal-значения для layout spacing/padding вроде `.padding(16)`, `VStack(spacing: 12)` или `.offset(y: 8)`.
- Используем существующие значения `Margin.x1`, `Margin.x2`, `Margin.x8` и т.п.
- Если нужного значения нет, сначала проверяем, действительно ли оно нужно. Затем добавляем его в `Margin`, а не локально в конкретный `View`.
- Исключения допустимы только для API, где число не является layout spacing, например `opacity`, `scaleEffect`, `lineLimit`, animation duration или chart/math constants.

## Constants

Константы выносим вниз файла в приватные extensions.

Обязательные правила:

- Не оставляем magic strings, magic numbers и повторяющиеся literal-значения внутри layout/business logic.
- Перед блоком файловых констант ставим один `// MARK: - Constants`.
- Файловые константы объявляем внизу файла через `private extension` подходящего типа: `CGFloat`, `Double`, `String`, `Int` или доменного типа.
- Константы группируем по типу значения, а не создаём глобальные `enum Constants` без необходимости.
- Если значение является частью reusable design system, выносим его в общий объект вроде `Margin`, `Font` или отдельный design token, а не в локальный extension файла.
- Literal-значения внутри `#Preview` не выносим в константы: preview должен оставаться самодостаточным и легко читаемым.
- Literal-значения допустимы inline, если они очевидны и не являются настраиваемыми константами: `0`, `1`, `true`, `false`, пустая строка в явном placeholder-контексте.

## Access Control

По умолчанию сужаем область видимости и поверхность изменения состояния.

Обязательные правила:

- Используем самый строгий access level, который не мешает реальному использованию: `private`, `fileprivate`, `internal`, `public`.
- Stored properties делаем `private`, если они не являются частью внешнего API типа.
- Для состояния, которое должно читаться извне, но изменяться только внутри типа, используем `private(set)`.
- Классы делаем `final`, если наследование явно не нужно.
- Типы, свойства и методы не делаем `public`/`internal` “на всякий случай”. Расширяем доступ только когда появился реальный внешний вызов.
- Не используем `private` механически, если это ухудшает тестируемость, SwiftUI preview ergonomics или требует искусственных wrapper-методов.

## Model Naming

Имена моделей должны отражать границу слоя, к которому они относятся.

Обязательные правила:

- SwiftData-модели, объявленные с макросом `@Model`, именуем с суффиксом `Model`, например `HistoryModel`.
- Сетевые транспортные модели именуем с суффиксом `DTO`, например `CalculationResponseDTO`.
- Доменные модели не получают технический суффикс слоя, например `CalculationInput` или `HistoryEntry`.
- Не добавляем `Model` к доменным и presentation-типам только потому, что они содержат данные.
- Presentation-типы при необходимости именуем по их назначению, например `HistoryViewState` или `HistoryRowViewData`.
